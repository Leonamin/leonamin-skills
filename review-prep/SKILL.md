# 리뷰 검수 자료 준비

## 역할

같은 리뷰 원칙을 서로 다른 프로젝트에 적용할 수 있도록 **무엇을 어디에서 찾아 비교해야 하는지** 기록한다. 특정 프레임워크, 디렉터리 이름, DB 제품을 가정하지 않는다. 이 스킬과 `review-run` 폴더를 함께 복사해 재사용할 수 있다.

공통 원칙은 [review-run의 검토 기준](../review-run/references/criteria.md)에 있다. 프로젝트에서 관찰한 패턴을 강제 규칙으로 자동 승격하지 않는다. 기존 중복이나 나쁜 설계를 표준으로 학습하지 않는다.

## 입력과 저장 위치

- 기본 대상은 현재 프로젝트다. 사용자가 지정한 프로젝트나 범위가 있으면 그것을 사용한다.
- Git 프로젝트는 root, HEAD, branch, status, worktree를 확인한다. Git이 없으면 디렉터리와 파일 지문으로 기준을 기록한다.
- 기본 산출물은 프로젝트 루트의 `.review-context/`다. 기존 자료나 사용자 지정 경로가 있으면 재사용한다.
- [자료 계약](references/context-contract.md)을 읽고 `index.md`와 필요한 영역별 자료를 생성·갱신한다. 관련 없는 영역의 빈 파일은 만들지 않는다.
- 제품 코드, 스키마, 기존 지침, CI 설정을 변경하지 않는다. 실제 리뷰 실행이나 PR 게시도 이 요청에 포함되지 않는다.

## 조사

1. 로컬 지침, 패키지/워크스페이스 설정, 진입점으로 언어·앱·패키지·배포 단위를 파악한다. 모노레포에서는 앱별 경계를 유지한다.
2. 공용 구현의 정의뿐 아니라 export, 대표 호출부, 테스트나 스토리를 확인한다. `shared`, `common` 같은 이름이나 사용 횟수만으로 표준을 지정하지 않는다. 외부 라이브러리와 프로젝트 wrapper의 관계도 기록한다.
3. 필요한 영역을 조사한다.
   - UI: 동작 요소, 입력, 알림, overlay, 레이아웃, 상태 표현의 책임과 지원 기능.
   - 에러 처리: handler, middleware, 응답 계약, 로깅, 사용자 메시지로 이어지는 경로.
   - 구조와 상태: 도메인 경계, 의존 방향, 서비스·훅·controller 등의 실제 책임과 사용 패턴.
   - 데이터: schema/model/migration에서 엔티티, 동일 사실의 소유자, 주요 관계, 쓰기 경로, 이력·스냅샷·캐시의 구분.
4. 각 영역을 `확인됨 / 후보 충돌 / 미발견 / 해당 없음 / 미조사`로 구분한다. `미발견`에는 검색 범위를, `해당 없음`에는 판단 근거를 남긴다. 전체 저장소를 확인하지 않았다면 전수 조사로 표시하지 않는다.
5. 명시된 프로젝트 정책은 출처와 적용 범위를 따로 기록한다. 관찰된 관행과 혼합하지 않는다. 자료가 충돌하면 어느 것을 강제할지 임의 결정하지 않고 충돌을 남긴다.

## 갱신

기존 기준 이후의 변경으로 영향을 받은 항목과 호출부를 재확인한다. 이동·삭제된 참조는 갱신하고, 과거 위치를 현재 위치처럼 남기지 않는다. 사용자 작성 설명·결정·예외는 보존하며 충돌을 표시한다.

생성 자료 자체, vendor, build, lockfile, 생성 코드를 공용 구현 탐색 결과로 오인하지 않는다. 런타임 DB 조회나 네트워크 연결 없이 로컬 자료로 시작하고, 배포된 스키마를 확인하지 않았다면 그 한계를 적는다. 비밀값, 환경 파일 내용, 운영 데이터는 수집하지 않는다.

## 완료 보고

저장 위치, 조사한 앱/영역, 미조사·충돌 항목과 기준 revision을 짧게 보고한다. 실제 코드리뷰가 끝났다고 표현하지 않는다. 후속 사용 예: `$review-run 기준 브랜치 대비 현재 브랜치를 리뷰해줘`.
