# 컴포넌트 인벤토리

**실제 사용자 흐름에 필요한 재사용 UI를 정하고, 기존 구현과 연결해 누락·중복을 줄인다.**

## 범위 결정

1. 플랫폼·사용자 흐름·도메인과 코드·Storybook·Figma·DESIGN.md의 기존 컴포넌트를 확인한다.
2. [Component Gallery](https://component.gallery/components/)는 누락을 찾는 참고 분류로 사용한다. 기본 요소·레이아웃·조합 패턴·페이지 구조처럼 책임과 추상화 수준으로 묶고, Gallery 항목마다 별도 컴포넌트를 만들거나 모두 구현하지 않는다. 최신 목록을 확인할 수 없으면 기존 자료를 사용하고 한계를 남긴다.
3. 아래 기본 체크리스트를 빠짐없이 훑고, 사용자 흐름에 필요한 도메인 항목을 추가한다. 각 항목을 기존 사용처와 대조해 판단하며, 도입 우선순위는 핵심 흐름의 중요도와 반복성으로 정한다.

## 기본 체크리스트

| 영역 | 확인할 요소 |
| --- | --- |
| 행동·이동 | 버튼, 아이콘 버튼, 링크, 메뉴, 탭, 탐색 경로 |
| 입력·선택 | 텍스트 입력·여러 줄 입력, 체크박스, 라디오, 스위치, 셀렉트, 날짜·파일 입력 |
| 폼 안내 | 라벨, 도움말, 필수·입력 제한, 검증 오류, 제출 중·중복 제출 방지 |
| 정보·목록 | 제목·본문, 목록·테이블, 검색·필터·정렬, 페이지 이동·더 보기 |
| 피드백·겹침 화면 | 알림, 로딩·진행 표시, 대화상자, 팝오버, 툴팁 |
| 상태·사용 조건 | 비활성, 빈 데이터·검색 결과 없음, 오류·재시도, 긴 콘텐츠, 좁은 화면, 키보드·포커스 |

플랫폼에 맞는 대응 요소로 확인한다. 모든 요소를 구현하라는 목록이 아니다. 아래 상태와 기존 구현 위치 또는 제외 이유를 남기고, 조사하지 못한 항목은 미확인으로 구분한다. 필요한 항목이 빠졌거나 미확인인데 누락 없음으로 보고하지 않는다.

| 상태 | 판단과 기록 |
| --- | --- |
| 기존으로 충족 | 기존 컴포넌트·조합·플랫폼 기본 요소로 충분함; 대응 항목 |
| 도입 | 필요한 기능과 재사용 근거가 있음; 범위·우선순위 |
| 통합 | 책임이 같고 이름·형태만 다름; 기준 항목 |
| 조건부 | 특정 요구가 생길 때 재검토; 재검토 조건 |
| 범위 밖 | 현재 제품에 필요하지 않음; 제외 이유 |

## 기록과 유지

- 프로젝트가 정한 문서·Figma·코드 원본에 기록한다. 경쟁 인벤토리를 만들지 않는다. 기준이 없으면 간결한 표를 제안하거나 요청된 산출물에 포함한다.
- 항목별 이름·책임·분류·상태·우선순위, 사용 흐름·제외 조건, 기존 대응 또는 도입 이유, 소유 역할과 문서·Figma·코드 매핑 중 필요한 정보를 남긴다.
- 도입 항목에는 목적·구성·콘텐츠·변형·상태·키보드·접근성·반응형·토큰·코드 매핑·안티패턴 중 해당하는 계약을 정한다. 불필요한 상태를 복제하거나 다른 책임을 거대한 컴포넌트로 합치지 않는다.
- 설계·구현 전 관련 항목을 확인한다. 기존 조합·변형으로 표현할 수 없고 재사용 근거가 있을 때 계약을 추가해 구현한다. 일회성 UI는 공용화하지 않는다.
- 새 요구가 겹치면 계약 확장·통합·별도 패턴 중 적합한 방식을 정한다. 구현·Figma·문서의 대응이 바뀌면 원본과 매핑을 함께 갱신한다.
- 구현까지 수행했다면 필요한 항목별로 실제 사용처와 관련 동작·상태의 검증 결과를 확인한다. 목록에 등록한 것만으로 구현·검증 완료로 표시하지 않는다.

인터랙션 통합은 `$standardize-interactive-components`, 제품 정체성·IA는 `$design-product`, DESIGN.md 기록·검증은 `$manage-design-md`를 필요할 때 사용한다.

검토한 자산·참조, 주요 결정과 이유, 발견한 누락, 갱신한 기준 위치와 미확정 항목을 보고한다.
