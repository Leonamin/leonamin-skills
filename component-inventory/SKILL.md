# 컴포넌트 인벤토리

새 화면을 만들 때 원시 요소를 매번 새 컴포넌트로 감싸거나, 이미 존재하는 패턴을 뒤늦게 추가해 디자인이 갈라지는 일을 줄인다. 결과물은 프로젝트에 맞는 재사용 컴포넌트 범위, 각 항목의 결정 상태, 누락을 막는 추가 절차다.

Component Gallery의 [컴포넌트 목록](https://component.gallery/components/)은 서로 다른 디자인 시스템의 사례를 모은 참고 분류다. 이를 요구사항 명세나 설치할 패키지 목록으로 취급하지 않는다. 목록에는 버튼·입력 같은 기초 요소와 표·탐색·페이지 패턴 등 추상화 수준이 다른 항목이 함께 있다.

## 범위 결정

1. 대상 플랫폼, 주요 사용자 흐름, 제품 도메인과 기존 디자인 자산을 확인한다. 저장소 코드, Storybook, Figma 라이브러리, `DESIGN.md` 및 기존 컴포넌트 문서를 살펴본다.
2. Component Gallery의 최신 분류를 확인할 수 있으면 항목을 검토한다. 네트워크를 쓸 수 없으면 현재 제공된 참고나 기존 목록을 사용하고, 최신 목록을 확인하지 못했다는 점을 결과에 남긴다.
3. 컴포넌트와 패턴을 추상화 수준에 따라 묶는다. 예를 들어 기본 요소·레이아웃 도구, 입력·선택, 메뉴·오버레이, 피드백·상태, 데이터·콘텐츠, 페이지 탐색·구조로 분류한다. Gallery의 각 항목을 그대로 별도 컴포넌트로 만들 필요는 없다.
4. 각 항목을 다음 중 하나로 판정한다.
   - **기존으로 충족**: 기존 컴포넌트나 플랫폼 기본 의미로 충분하다. 대응 항목을 적는다.
   - **도입**: 제품 흐름에 필요하고 재사용할 근거가 있다. 만들 범위와 우선순위를 정한다.
   - **통합**: 다른 항목과 같은 책임이며 이름이나 형태만 다르다. 기준 항목을 정한다.
   - **조건부**: 특정 기능·도메인·플랫폼이 생길 때 재검토한다. 조건을 적는다.
   - **범위 밖**: 현재 제품에 필요하지 않다. 제외 근거를 간단히 적는다.
5. 사용자가 실제로 만드는 화면과 사용자 흐름에 항목을 대조해 빠진 공통 동작을 찾는다. 우선순위는 사용자 흐름의 중요도와 반복성으로 정한다. 목록을 모두 `도입`으로 표시하거나 아직 쓰이지 않을 컴포넌트를 미리 전부 구현하지 않는다.

## 인벤토리 기록

기존 디자인 시스템의 단일 기준 위치를 사용한다. `DESIGN.md`, 컴포넌트 문서, Figma 라이브러리 또는 코드 중 프로젝트가 정한 원본을 먼저 확인하고, 별도 인벤토리 파일을 무조건 추가하지 않는다. 기준이 없으면 합의된 문서에 간결한 표를 제안하거나 요청된 산출물에 포함한다.

각 항목에는 필요한 만큼 다음을 기록한다.

- 이름과 책임, 분류, 결정 상태 및 우선순위
- 적용할 사용자 흐름과 사용하지 않을 상황
- 기존 대응 항목 또는 추가가 필요한 이유
- 책임자 역할과 기준 문서·Figma·코드 매핑
- 조건부 또는 범위 밖 결정의 근거

도입을 결정한 컴포넌트에는 해당 유형에 필요한 계약을 정의한다. 기본 계약은 목적, 구성과 콘텐츠, 변형·상태, 키보드·접근성 동작, 반응형 동작, 디자인 토큰, 코드 매핑, 안티패턴이다. 모든 컴포넌트에 불필요한 상태를 기계적으로 복사하지 말고 실제 사용 방식에 맞춘다.

기초 요소와 조합 패턴의 경계를 명확히 한다. 버튼·링크·폼 필드·레이아웃 유틸리티 같은 반복 기초 요소는 안정적인 계약을 갖게 한다. 카드·표·검색·날짜 선택기 같은 조합 요소는 필요한 사용자 흐름과 변형을 확인한 뒤 도입한다. 서로 다른 시각 언어와 동작을 하나의 거대한 컴포넌트로 합치지 않는다.

## 누락 방지와 유지보수

- 화면을 설계하거나 구현하기 전에 인벤토리의 관련 범주를 확인한다. 화면에 필요한 항목이 없으면 새로 만들기 전에 기존 컴포넌트의 조합이나 변형으로 표현 가능한지 살핀다.
- 기존 계약으로 표현할 수 없고 재사용 근거가 있으면, 인벤토리와 기준 문서에 목적·범위·계약을 추가한 뒤 구현한다. 일회성 화면 요소라면 공용 컴포넌트로 승격하지 않는다.
- 새 요구가 기존 항목과 겹치면 중복 생성보다 기존 계약 확장, 통합 또는 별도 패턴 중 무엇이 맞는지 판단하고 이유를 기록한다.
- 구현, Figma 라이브러리와 기준 문서 사이의 대응이 달라지면 원본과 매핑을 함께 갱신한다. 코드 수준의 인터랙션 통합 및 회귀 방지는 `$standardize-interactive-components`를 사용한다.
- 디자인 시스템의 큰 정체성·정보 구조 결정은 `$design-product`, `DESIGN.md` 기록·검증은 `$manage-design-md`와 협업한다. 각 도구의 작업 범위를 인벤토리 작업으로 대체하지 않는다.

## 완료 보고

검토한 참조와 자산, 분류 기준, 도입·통합·조건부·범위 밖 결정, 발견한 빈칸, 갱신한 기준 위치를 보고한다. 최신 Gallery 목록을 확인하지 못했거나 제품 요구가 불명확한 항목은 사실처럼 채우지 말고 미확정으로 표시한다.
