# 프로젝트 공통 검토 기준

모든 프로젝트에서 같은 질문을 사용하고, 답에 필요한 구현과 계약은 해당 프로젝트에서 찾는다. 언어와 프레임워크마다 특정 파일 구조나 추상화 계층을 강제하지 않는다. 명시적 프로젝트 정책이 있다면 범위를 확인해 함께 적용한다.

| ID | 검토 질문 | 지적에 필요한 근거 | 정당한 차이의 예 |
|---|---|---|---|
| REUSE-UI | 새 UI나 기본 요소가 기존 공용 요소의 책임을 반복하는가? | 기존 API가 필요한 상태·접근성·동작을 지원하며 해당 위치에서 사용할 수 있다는 근거 | primitive 내부의 HTML, 다른 접근성 의미, 지원하지 않는 상호작용 |
| REUSE-LOGIC | 새 helper/service/변환 로직이 기존 구현과 같은 계약을 다시 구현하는가? | 입력·출력·예외·부작용 비교와 실제 사용처 | 앱 간 의존 제한, 다른 도메인 정책, 외형만 같은 계산 |
| ERROR-FLOW | 로컬 에러 처리가 공용 처리 경로를 우회하는가? | 기존 handler/middleware의 적용 가능성, 누락되는 로깅·응답·정리·메시지 계약 | 경계 안에서 복구 가능한 예외, 공용 handler 자체의 내부 처리 |
| RESPONSIBILITY | 서로 다른 변경 이유를 가진 책임이 한 파일/모듈에서 얽혔는가? | 어떤 책임이 어떤 상태·의존성을 공유하며 독립 변경이나 검증을 방해하는지 | 응집도 높은 단일 기능, 분리하면 오히려 전달과 간접 참조만 늘어나는 코드 |
| STATE-COMPLEXITY | 훅·effect·분기 간 결합이 상태 일관성이나 이해를 어렵게 하는가? | 동기화해야 하는 중복 상태, 의존 순환, 중첩 분기의 실제 경로, 누락 상태 | 독립적이고 단순한 여러 훅, 읽기 쉬운 단일 조건식 |
| DATA-OWNERSHIP | 새 테이블·컬럼이 기존과 같은 사실을 이중 소유하는가? | 의미·생명주기·writer·제약조건 비교, 불일치가 생기는 갱신 경로 | 이력, 거래 당시 snapshot, 근거 있는 비정규화와 일관성 유지 계약 |

## 숫자와 원칙의 사용

300줄 이상 파일, 훅 5개 이상, 삼항연산자 등은 집중 검토 신호다. 숫자만으로 위반을 확정하지 않는다. 명시적 프로젝트 금지 규칙은 정책 위반으로 보고하되 런타임 버그와 구분한다. `SOLID 위반`, `분리 필요`만으로 지적을 끝내지 않는다. 책임, 영향과 유효한 분리 경계를 설명한다.

분리 자체를 목표로 새 계층이나 훅을 만들도록 요구하지 않는다. 단순 복제 축소와 실제 계약 재사용을 구분한다. 사용 가능한 적절한 공용 구현이 없으면 신규 구현은 정상일 수 있다.

## 근거와 중요도

- 재사용 지적은 대체 후보의 실제 정의와 호출부를 읽은 경우에만 확정한다. 후보가 없으면 탐색 범위와 판단 한계를 남긴다.
- DB 의미는 이름만으로 추론해 확정하지 않는다. 소유권·생명주기를 확인할 수 없다면 판단 보류다.
- 사용자 영향, 데이터 불일치, 반복되는 유지보수 부담과 명시적 정책 위반을 설명한다. 취향이나 가상의 미래 확장성만으로 수정 필요 판정을 내리지 않는다.
- `높음`: 데이터 손상, 잘못된 권한/응답, 주요 기능 실패 등 구체적인 중대 영향.
- `보통`: 적용 가능한 공용 계약의 중복/우회, 확인된 책임 결합이나 상태 결함으로 수정이 필요한 경우.
- `낮음`: 영향이 작은 개선 제안. 이 항목만으로 통과를 막지 않는다.
- 근거 없는 수치 확신도를 만들지 않는다. 반례를 확인해도 판단에 필요한 자료가 부족하면 미확정으로 남긴다.
