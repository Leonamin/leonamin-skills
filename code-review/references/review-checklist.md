# 아키텍처 리뷰

변경된 코드만 고립해 보지 말고 호출자, 피호출자, 관련 모듈과 설정을 함께 읽는다. 문서에 적힌 구조와 실제 import·호출 구조가 다르면 실제 구조를 기준으로 판단한다.

## 검토 항목

- 모듈과 계층의 책임이 명확한가
- 의존성이 허용된 방향으로 흐르는가
- 도메인 로직이 UI, 저장소, 프레임워크 세부사항에 불필요하게 묶이지 않는가
- 공개 API, 데이터 계약, 이벤트와 오류 계약의 변경 영향이 관리되는가
- 하나의 변경이 여러 책임과 변경 이유를 함께 끌어안지 않는가
- 기존 추상화가 있는데 새 경로가 우회하거나 중복 구현하지 않는가

## 보고 기준

구조적 취향보다 구체적인 결합도 증가, 순환 의존, 책임 누수, 호출자 회귀 가능성을 근거로 보고한다. 작은 중복보다 잘못된 경계와 외부 계약 변경을 높은 우선순위로 둔다.

# 언어 품질 리뷰

언어와 버전을 먼저 확인하고 저장소의 컴파일러·린터·LSP 진단을 우선 근거로 사용한다. 언어 문법 자체보다 변경으로 발생할 수 있는 실제 오류를 우선한다.

## 검토 항목

- 타입 안전성, null/undefined 처리, 암묵적 변환, 비동기·예외 전파
- 언어의 값/참조 의미, 가변성, 수명, 동시성 모델에서 발생할 수 있는 오류
- 표준 라이브러리와 프로젝트가 채택한 관용적 API 사용 여부
- compiler, linter, formatter, LSP 진단과의 불일치
- 새 추상화가 언어의 타입 시스템이나 런타임 동작을 우회하는지 여부

## 진행

1. `package.json`, `pyproject.toml`, `go.mod`, compiler 설정 등으로 언어와 버전을 확인한다.
2. 가능한 경우 기존 검증 명령을 실행하거나 진단 결과를 확인한다.
3. 언어 규칙 위반이 실제 동작·빌드·유지보수에 미치는 영향을 설명한다.
4. 프로젝트 관례와 충돌하지 않는 최소 수정안을 제안한다.

LSP는 편집기 진단을 보조 근거로만 사용한다. 진단이 없다는 사실을 코드의 정확성 증명으로 취급하지 않는다.

# 소프트웨어 공학 리뷰

규칙을 암기식으로 적용하지 말고 변경의 실패 모드와 운영 비용을 중심으로 판단한다.

## 검토 항목

- 정상·경계·실패 경로가 테스트로 보호되는가
- 오류를 삼키거나 잘못된 성공으로 바꾸지 않는가
- 책임과 제어 흐름이 과도하게 복잡하지 않은가
- 중복이 실제로 함께 변경될 지식을 복제하는가
- 외부 호출, 재시도, 타임아웃, 멱등성이 적절한가
- 로그·메트릭·추적 등 장애 원인을 확인할 수 있는가
- 변경이 기존 동작과 호환되는가

## 판단 기준

테스트가 없다는 사실만으로 문제 삼지 말고 변경된 위험 경로가 검증되지 않았는지 설명한다. 추상화·리팩터링은 코드가 짧아지는지보다 변경 이유와 실패 격리를 개선하는지로 평가한다.

# 네이밍 리뷰

변경된 코드의 이름이 타입이나 표면적인 Case 규칙보다 **역할과 의미를 정확히 표현하는지** 검토한다. 언어별 대소문자 규칙과 포매팅은 언어 도구와 기존 프로젝트 관례에 맡긴다.

## 변수와 필드

- 값은 의미를 나타내는 명사구를 사용한다. 단위가 중요하면 이름에 단위를 포함한다(`timeoutMs`, `retryCount`).
- 컬렉션은 복수형이나 자료구조가 드러나는 이름을 사용한다(`users`, `userById`, `userIds`).
- Boolean은 상태·조건을 숨기지 않도록 조동사 또는 존재 표현을 앞에 둔다.
  - `is...`: 상태 또는 조건
  - `has...`: 보유·존재 여부
  - `can...`: 권한·가능 여부
  - `should...`: 권장·지연된 의도
  - `needs...`: 요구 여부
- `ready`, `loading`, `valid`, `recommended`처럼 접두사 없는 Boolean 이름은 의미가 모호할 때 지적한다.
- 부정형보다 긍정형을 우선한다(`isEnabled` > `isNotDisabled`). 단, 도메인에서 부정 상태가 핵심이면 예외로 둔다.

## 함수와 메서드

- 동작을 동사로 시작하고 대상과 결과를 이름에 포함한다(`findUser`, `calculateTotal`, `toDisplayName`).
- 조회·검색·변환·검증·생성·변경의 차이를 이름에 반영한다.
  - `get`: 이미 존재하는 값을 읽음
  - `find`: 없을 수 있는 값을 찾음
  - `list`: 여러 항목을 반환함
  - `parse`/`to`: 형식 또는 표현을 변환함
  - `validate`/`is`: 유효성 또는 조건을 판정함
- `handle`, `process`, `do`, `manage`처럼 동작과 결과가 드러나지 않는 이름은 실제 책임을 설명할 수 있을 때까지 지적한다.
- Boolean을 반환하는 함수도 `is...`, `has...`, `can...`, `should...`, `needs...` 형식을 따른다.
- 함수가 이름에 표시된 대상보다 훨씬 많은 책임을 가지면 이름을 억지로 늘리지 말고 책임 분리를 제안한다.

## 클래스와 타입

- 클래스와 주요 타입은 하나의 책임을 나타내는 명사 또는 명사구를 사용한다(`Invoice`, `PaymentPolicy`, `UserRepository`).
- `Manager`, `Helper`, `Util`, `Data` 같은 범용 접미사는 실제 책임이 이름에 드러나지 않을 때 지적한다.
- 구현체·어댑터·정책·저장소처럼 역할이 중요한 경우 역할을 명시한다(`StripePaymentGateway`, `TaxPolicy`).
- 이름과 실제 책임의 범위가 어긋나면 이름 변경만으로 덮지 말고 클래스 분리 또는 책임 축소를 제안한다.

## 리뷰 원칙

1. 먼저 같은 프로젝트의 기존 이름과 도메인 용어를 확인한다.
2. 단순 취향 차이, Case 스타일, 포매터가 해결할 문제는 지적하지 않는다.
3. 이름만 보고 의미를 추측해야 하거나 호출부에서 오해할 가능성이 있을 때만 지적한다.
4. 각 코멘트에 문제의 의미, 영향, 구체적인 대안을 짧게 제시한다.
5. 확신이 낮으면 `suggestion`으로 표현하고 동작 오류로 단정하지 않는다.
