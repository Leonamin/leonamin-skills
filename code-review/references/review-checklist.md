# 코드 리뷰 검토 기준

**규칙의 모양보다 변경의 실패 조건과 실제 영향을 판단한다. 필요한 관점만 적용한다.**

## 아키텍처

- 호출자·피호출자·모듈·설정을 함께 확인한다. 문서와 import·호출 구조가 다르면 실제 동작을 기준으로 판단한다.
- 책임·의존 방향, 순환 참조, 도메인과 UI·저장소·프레임워크의 결합을 확인한다.
- 공개 API·데이터·이벤트·오류 계약 변경이 호출자에 미치는 영향과 기존 추상화의 우회·중복을 확인한다.
- 구조적 취향 대신 책임 누수·결합 증가·실제 회귀를 보고한다. 작은 중복보다 잘못된 경계와 외부 계약 변경을 우선한다.

## 언어 동작

- 의존성·compiler 설정으로 언어와 버전을 확인하고 기존 compiler·linter·LSP 진단을 활용한다.
- 타입·null·암묵적 변환, 값/참조·가변성·수명, 비동기·예외 전파·동시성에서 생길 오류를 확인한다.
- 표준·프로젝트 API의 계약과 새 추상화가 우회하는 타입·런타임 조건을 확인한다.
- 진단 부재를 정확성의 증명으로 보지 않는다. 관례에 맞는 최소 수정안을 제시한다.

## 실패 경로와 운영

- 정상·경계·실패 경로, 오류 삼킴·거짓 성공, 외부 호출·재시도·타임아웃·멱등성과 기존 호환성을 확인한다.
- 장애 원인을 찾을 로그·메트릭과 제어 흐름의 복잡성, 함께 변경될 지식의 중복을 검토한다.
- 테스트 부재 자체보다 검증되지 않은 위험 경로를 설명한다. 추상화는 줄 수보다 변경 이유와 실패 격리를 개선하는지 판단한다.

## 이름의 의미

프로젝트 규칙·도메인 용어를 먼저 확인한다. 이름이 호출부에서 실제 오해를 만들 때 지적하며 대소문자·포매팅 취향은 언어 도구와 프로젝트 관례에 맡긴다.

- 값·컬렉션의 대상·단위·구조와 상태·조건이 이름에 드러나는가?
- 함수의 조회·검색·변환·검증·변경 의미가 실제 반환값·부수 효과와 일치하는가?
- `handle`·`process`·`Manager`·`Helper`처럼 넓은 이름이 책임을 숨기는가?
- 이름보다 책임이 크면 긴 이름으로 덮기보다 분리·축소를 제안한다.

프로젝트에 없는 네이밍 규칙을 새로 강제하지 않는다. 의미·영향·구체적 대안을 제시하고 확신이 낮은 개선은 `suggestion`으로 구분한다.
