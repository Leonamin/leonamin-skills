# 코드 리뷰 오케스트레이터

변경사항을 먼저 이해하고 필요한 전문 리뷰만 선택해 중복 없이 통합한다. 모든 규칙을 무조건 적용하지 않는다.

## 흐름

1. diff와 주변 코드를 읽고 변경 목적, 영향 범위, 사용 언어와 프로젝트 도구를 파악한다.
2. 리뷰 축을 선택한다.
   - 모든 변경: correctness와 회귀 위험
   - 이름·식별자 변경: `naming-rules`
   - 언어 문법·타입·컴파일러 진단: `language-review`
   - 모듈·계층·의존성·공개 API 변경: `architecture-review`
   - 테스트·오류 처리·복잡도·유지보수성: `engineering-practices-review`
3. 선택한 축의 규칙과 프로젝트 선례를 적용한다. 사용 가능한 전문 스킬이 있으면 해당 스킬의 책임을 따른다.
4. 실제 문제, 개선 제안, 단순 취향을 구분하고 같은 원인의 코멘트는 합친다.
5. 파일과 행을 특정할 수 있는 근거만 보고한다. 수정은 사용자가 요청했을 때만 수행한다.

## 결과 형식

심각도 순으로 보고한다.

- `blocker`: 동작 오류, 보안 문제, 데이터 손실, 명백한 회귀
- `major`: 중요한 유지보수·구조·테스트 문제
- `minor`: 오해를 유발하거나 국소적으로 개선할 수 있는 문제
- `suggestion`: 선택 가능한 개선

각 항목은 `심각도 · 파일:행 · 문제 · 영향 · 제안` 순서로 짧게 작성한다. 발견 사항이 없으면 무엇을 확인했고 위험이 낮은 이유를 요약한다.

## 경계

- 포매팅과 자동 린트 결과를 사람이 판단한 설계 문제처럼 반복하지 않는다.
- 프로젝트의 명시적 규칙과 기존 관례를 일반적인 취향보다 우선한다.
- 리뷰 범위 밖의 문제는 별도 후속 항목으로 분리한다.
