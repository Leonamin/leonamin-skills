# UI Before/After Sketch

## 역할과 범위

실제 제품 코드를 바꾸기 전에 현재 구조와 제안 구조의 차이를 빠르게 확인할 수 있는 저비용 시안을 만든다.

- `Before`: 제공된 화면·스크린샷·코드에서 확인한 현재 상태를 충실하게 재현한다.
- `After`: 사용자가 요청한 개선만 반영한다. unrelated redesign를 섞지 않는다.
- 결과물: HTML, CSS, 브라우저 렌더링 PNG, 짧은 변경 요약과 구현 시 고려사항.

이 스킬은 구현물이 아니라 의사결정용 시안이다. 기본값은 읽기 전용이며 실제 제품 소스, 배포 환경, DB를 수정하지 않는다. 스킬 폴더의 `scripts/capture_html_screenshot.sh`만 사용해 정적 HTML을 캡처하며, 다른 스킬의 파일·설정·메모리·명령을 요구하지 않는다. 브라우저 캡처 명령이 설치되어 있지 않으면 설치 방법을 안내하고 캡처를 검증되지 않은 방식으로 대체하지 않는다.

## 작업 흐름

### 1. 범위와 근거 고정

다음 중 제공된 근거를 우선순위대로 확인한다.

1. 실제 route 또는 로컬 화면
2. 저장소의 실제 component, shared primitive, design token
3. 사용자가 첨부한 스크린샷
4. 설명만 있는 경우에는 확인하지 못한 부분을 표시하고 최소한의 합리적 가정을 사용한다.

대상 viewport와 상태를 정한다. 예: 데스크톱 1440×1024, 모바일 390×844, 검색 전, 검색 후, 저장 전, 변경 후.

### 2. Before 분석

다음 항목을 1~3개로 압축한다.

- 중첩 카드·테이블 프레임·불필요한 경계
- 정보 계층과 밀도
- 액션과 상태의 가시성
- 모바일 overflow·도달성
- 반복되는 접근성 이름 또는 안내 부족

Before에 존재하지 않는 기능·데이터·배지를 만들어 문제를 감추지 않는다.

### 3. HTML/CSS 시안 작성

작업별 시각화 디렉터리에 `index.html`과 `styles.css`를 만든다. 저장소 소스 옆에 임시 파일을 남기지 않는다. 시각화 디렉터리는 프로젝트가 지정한 임시·산출물 위치를 우선하고, 지정이 없으면 작업 디렉터리 밖의 임시 위치를 사용한다.

- `Before`와 `After`는 기본적으로 좌우가 아닌 상하로 배치한다. 각 패널은 viewport의 가로 폭을 최대한 사용해야 하며, 비교용 wrapper 때문에 화면이 임의로 절반으로 축소되지 않게 한다.
- 두 패널은 같은 viewport 안에서 동일한 가로 기준으로 비교하고 `BEFORE`, `AFTER`를 명확히 표시한다. CSS에서는 `grid-template-columns: 1fr 1fr` 또는 절반 폭의 flex item을 기본값으로 사용하지 말고, `grid-template-columns: minmax(0, 1fr)`와 행 방향 배치 또는 세로 flex 레이아웃을 사용한다.
- 모든 문자열을 `제품 UI 문자열`과 `시안 전용 설명`으로 먼저 분류한다. 실제 화면·코드·요청에서 확인한 제품 UI 문자열만 UI 내부에 넣고, 확인하지 못한 문구를 제품 카피처럼 추정해 만들지 않는다.
- 시안 전용 설명은 실제 UI 영역 안에 섞지 않는다. 패널 바깥의 별도 주석 영역 또는 별도 callout으로 배치하고, HTML에서도 `data-sketch-only="true"`와 `sketch-annotation` 같은 명시적인 표식을 사용한다.
- 시안 전용 설명에는 항상 `SKETCH NOTE · NOT FOR IMPLEMENTATION` 같은 고정 라벨을 붙이고, 점선 테두리·주석 전용 색상·작은 보조 타이포그래피 등 제품 UI와 확연히 다른 스타일을 적용한다. 제품의 버튼·배지·본문처럼 보이는 스타일로 설명을 위장하지 않는다.
- 실제 구현 시 복사할 범위를 `.ui-surface` 같은 제품 UI 컨테이너 내부로 한정하고, `sketch-annotation`, `data-sketch-only="true"` 및 그 내용은 제거하도록 HTML에 주석으로 경계를 남긴다.
- 실제 화면에서 확인한 문구·컬럼·상태·토큰을 재사용한다.
- 프로젝트의 기존 색상·spacing·radius·typography를 우선 사용한다.
- After에는 변경된 부분이 눈에 보이도록 경계, 밀도, 액션 상태를 비교한다.
- 필요하면 변경된 상태를 별도 작은 예시로 표시한다. 예: clean state와 dirty state.
- 반응형 문제가 범위에 있으면 데스크톱과 모바일을 각각 렌더링한다.
- CSS gradient, 임의의 장식 이미지, 과도한 shadow, 가짜 브랜드 요소를 추가하지 않는다.

### 4. 브라우저 렌더링

스킬 폴더 기준으로 재사용 캡처 스크립트를 실행한다. 먼저 `agent-browser --version`으로 브라우저 CLI가 있는지 확인한다.

```bash
<skill-dir>/scripts/capture_html_screenshot.sh \
  <path-to-index.html> <output.png> [width] [height]
```

이 스크립트는 정적 HTML을 `file://` URL로 열고 `agent-browser`로 렌더링한 뒤 전체 페이지 PNG를 저장한다. `agent-browser`는 이 스킬이 제공하는 CLI 의존성이며 다른 스킬을 호출하지 않는다. 렌더링 후 이미지 뷰어로 직접 확인하고, 잘림·overflow·텍스트 겹침·Before/After 불균형이 있으면 CSS를 수정해 다시 캡처한다.

### 5. 결과 전달

최종 응답은 다음 순서로 짧게 전달한다.

1. Before/After PNG를 먼저 보여준다.
2. 바뀐 구조를 2~4개 항목으로 설명한다.
3. HTML/CSS 산출물 링크를 제공한다.
4. 실제 소스는 수정하지 않았는지, 다음 구현 범위를 명시한다.
5. 브라우저 검증 viewport와 남은 가정을 적는다.
6. 제품 UI 문자열과 시안 전용 설명을 구분하는 방법 및 실제 구현에서 제외할 범위를 명시한다.

## 품질 기준

- Before와 After는 같은 데이터·같은 viewport·같은 상태를 비교한다.
- 제품 UI 문자열과 시안 전용 설명은 시각적·구조적으로 구분되며, 후자는 제품 UI 컨테이너 밖에 있다.
- 개선안은 한 화면에서 핵심 차이가 즉시 보인다.
- After가 단순히 더 예쁜 화면이 아니라 문제를 해결하는 구조인지 설명할 수 있다.
- 실제 디자인 토큰을 확인하지 못했으면 임의의 토큰을 제품 규칙처럼 단정하지 않는다.
- 스크린샷을 만들었다고 production 구현이나 검증 완료로 표현하지 않는다.
- 사용자가 이후 구현을 요청하면 이 시안을 기준으로 해당 프로젝트의 일반 구현 절차를 따른다. 특정 스킬이나 도구로 넘기는 것을 완료 조건으로 삼지 않는다.

## 중단 조건

- 사용자가 지정한 실제 화면·파일·Figma가 접근되지 않고, 그 차이가 Before 재현에 중요하면 임의로 만들지 말고 확인을 요청한다.
- 실제 제품 source를 수정해야만 비교 가능한 경우에는 이 스킬의 읽기 전용 범위를 설명하고 구현 승인을 별도로 받는다.
- 인증이 필요한 live route는 읽기 전용 smoke check만 수행하며 계정 정보나 비밀값을 출력하지 않는다.
