# Make Prototype

**핵심 사용자 흐름이 작동하는 앱을 만들고, 구조·재사용·디자인·동작을 검수해 완료한다.**

구현 요청에는 필요한 설계·리팩터링·검증을 포함한다. 상담에는 제안을 제공한다. 배포·외부 메시지·운영 데이터 변경은 별도 요청 범위다.

## 1. 범위와 기준

- 프로젝트 지침·기존 코드·스택·검증 명령과 디자인·아키텍처 기준을 확인한다. 관련 결정이 위키에 있으면 필요한 부분을 읽는다.
- 핵심 흐름·화면·데이터·액션, 실제 연동과 mock의 경계, 완료 조건을 정한다. 고위험의 모호함은 질문하고 되돌릴 수 있는 선택은 가정을 밝히고 진행한다.
- 기존 스택·결정을 우선한다. 새 프로젝트는 필요한 최소 스택과 짧은 설계 기록으로 시작한다. 문서는 기존 위치에 갱신하고 코드와 중복된 계획·상태 파일을 늘리지 않는다.

## 2. 구조와 구현

- 앱 루트는 provider·라우팅·조립, 페이지는 화면 구성을 담당한다. 재사용 UI·업무 규칙·외부 접근을 한 파일에 몰아넣지 않는다.
- 공용 UI는 기본 요소·레이아웃·조합 패턴을 책임에 맞게 구분하고 도메인에 의존하지 않는다. 업무 용어를 아는 UI·훅·데이터 접근은 기능 가까이에 둔다. 기존 라이브러리의 `components/ui` 관례는 유지하되 모든 앱 코드나 무의미한 래퍼를 넣지 않는다.
- 새 구현 직전에 책임·사용처로 기존 코드를 검색한다. 재사용 → 조합/variant 확장 → 도메인 구현 → 공용 추상화 순으로 판단한다. 같은 책임의 두 번째 구현은 통합하고, 모양만 비슷한 기능은 억지로 합치지 않는다.
- 공유 shell·navigation·header를 조합하되 과도한 boolean prop으로 화면 차이를 밀어 넣지 않는다. 불필요한 폴더·계층·패키지나 일회성 JSX 분리를 만들지 않는다.
- 상태 소유자와 파생 값을 정하고 복제·불필요한 전역화를 피한다. 저장 범위와 URL·새로고침·뒤로가기 동작을 명확히 한다.
- 첫 핵심 흐름부터 구현한다. 액션은 상태·데이터·경로를 실제로 바꾸고, mock·실패 시뮬레이션은 교체 가능한 데이터 경계에 둔다. 범위 밖 기능과 mock 성공을 실제 연동으로 표현하지 않는다.

서버나 도메인 간 경계를 다룰 때 [구조와 경계](references/architecture.md)를 읽는다.

## 3. 디자인과 상태

- 색상·간격·타이포·radius·elevation·너비·반응형 기준을 토큰으로 정하고 실제 참조한다. 일회성 값은 무조건 공용화하지 않는다. 기준 문서와 실행 토큰의 원본·파생 관계를 유지한다.
- 필요한 제목·본문·라벨 위계를 정의하되 모든 역할을 화면마다 채우지 않는다. 헤더의 설명·상단 라벨은 선택 항목으로 두고 [UI 문구 절제 기준](../design-product/references/ui-copy.md)을 적용한다.
- 제품 UI의 장식·상태·액션에는 이모지 대신 일관된 아이콘 세트를 사용한다. 사용자 콘텐츠는 변조하지 않는다. 아이콘 액션에 접근 가능한 이름을 주고 장식 아이콘은 숨기며 색상·아이콘만으로 상태를 전달하지 않는다.
- 실제 필요한 로딩·빈 결과·오류·성공·검증·비활성 상태를 구현한다.
- 웹 프론트엔드에는 기본적으로 Storybook을 연동하고 [상태 재현 기준](references/storybook.md)을 적용한다. 비웹·사용자 제외·지원 제약은 이유와 범위를 명시한다. 기존 설정을 재생성하거나 버전을 일괄 업그레이드하지 않는다. **자식 단독 스토리는 실제 부모 화면의 상태 재현을 대체하지 않는다.**

## 4. 검수와 완료

[완료 검수](references/completion-review.md)로 범위 내 결함을 수정하고 관련 검증을 다시 수행한다. 구현한 흐름, 구조·재사용 결정, 실행 방법, 검증, mock·미검증 범위를 보고한다. 고장 난 핵심 흐름이나 중복을 후속 개선으로 떠넘기지 않는다.

## 필요한 스킬만 적용

디자인·IA는 `$design-product`, 공용 UI 범위는 `$component-inventory`, DESIGN.md 관리는 `$manage-design-md`, 인터랙션 통합은 `$standardize-interactive-components`, 화면 감사는 `$design-audit`, 코드 검토는 `$code-review`, 브라우저 검증은 환경의 도구나 `$agent-browser`를 사용한다. 사용 가능한 스킬을 필요한 단계에서만 읽고, 없으면 위 기준으로 수행한다. 이미지 시안·Figma·Before/After는 요청이나 시각적 불확실성이 있을 때만 추가한다.
