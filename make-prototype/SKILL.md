# Make Prototype

한 번의 구현 요청을 구조·디자인·구현·검수까지 완료한다. 사용자가 단계별로 다시 요청해야만 구조와 품질을 정리하는 방식으로 끝내지 않는다. 설계 상담이면 결합 방식과 선택지를 설명하고 구현을 임의로 시작하지 않는다.

## 1. 범위와 기준 확보

- 프로젝트 지침, 기존 코드·의존성·검증 명령, DESIGN.md·토큰·공용 컴포넌트, 아키텍처 문서·ADR을 먼저 읽는다. 기존 위키가 관련 결정을 소유하면 사용 가능한 `$wiki-read`로 필요한 결정만 확인한다.
- 핵심 사용자 흐름, 화면/경로, 필요한 데이터와 액션, 실제 연동과 mock의 경계, 완료 조건을 짧게 정한다. 모호한 고위험 결정만 질문하고 되돌리기 쉬운 선택은 가정을 밝히고 진행한다.
- 기존 스택과 구조를 존중한다. 새 프로젝트는 요구에 필요한 최소 스택을 고른다. 프로토타입이라는 이유로 거대 엔트리 파일을 만들거나, 미래 확장을 이유로 불필요한 계층·패키지를 만들지 않는다.
- 구현 요청은 내부 설계·리팩터링·검증을 포함한다. 별도 요청 없는 배포, 외부 메시지 전송, 운영 데이터 변경으로 범위를 확대하지 않는다.

## 2. 필요한 기존 스킬 결합

사용 가능한 스킬을 확인하고 해당 단계에서 원문을 읽어 적용한다. 아래 스킬을 전부 일괄 로드하거나 결과마다 별도 보고서를 만들지 않는다. 없는 스킬은 이 문서의 기준으로 수행하고, 작업에 실제로 필요한 기능이 막힌 경우만 한계를 알린다.

| 상황 | 사용할 스킬 | 이번 작업에서 필요한 결과 |
| --- | --- | --- |
| 제품/디자인 방향과 IA가 없음 | `$design-product` | 사용자 흐름, 시각 방향, 디자인 기준 |
| 공유 UI의 범위·중복·계약 결정 | `$component-inventory` | 실제 화면에 필요한 항목과 코드 위치, 재사용 계약 |
| DESIGN.md를 기준으로 채택하거나 유지 | `$manage-design-md` | 토큰·타이포그래피·컴포넌트 계약과 형식 검증 |
| 반복 인터랙션을 구현·통합 | `$standardize-interactive-components` | 버튼·링크·선택의 의미, 키보드 동작, 접근성 |
| 실행 화면의 디자인 결함 점검 | `$design-audit` | 이번 흐름의 위계·반응형·상태 표현 결함 수정 |
| 브라우저 동작 확인 | `$agent-browser` 또는 환경의 브라우저 도구 | 핵심 흐름을 실행한 증거 |
| 코드의 경계·정확성 최종 검토 | `$code-review` | 발견한 실제 결함 수정과 재검증 |

이미 정해진 방향을 다시 설계하지 않는다. 이미지 시안·Figma·Before/After 산출물은 사용자 요청 또는 해결해야 할 시각적 불확실성이 있을 때만 추가한다. 상담이나 기존 근거만으로 충분한 작업에 이를 선행 조건으로 붙이지 않는다.

## 3. 구현 전에 작은 계약 정하기

문서는 기존 기준 위치에 필요한 만큼만 기록한다. 새 프로젝트에 기준이 없으면 짧은 설계 기록을 두되, 코드와 중복된 별도 계획·상태·보고 파일을 늘리지 않는다.

### 구조와 책임

- 엔트리/앱 루트는 provider, 라우팅, 앱 조립을 담당한다. 페이지는 화면 구성을 담당하며, 재사용 UI·업무 규칙·외부 접근 구현을 한 파일에 몰아넣지 않는다.
- 공용 코드는 책임별로 구분한다: 기본 조작/표현을 담당하는 `primitives`, 레이아웃 도구, 공용 조합 패턴, 앱 레이아웃. 폴더는 실제 코드가 필요할 때 만들고 모든 것을 `components/ui`에 넣지 않는다.
- 업무 용어·규칙을 아는 컴포넌트, 훅, 데이터 접근은 해당 도메인/기능 가까이에 둔다. 도메인 전용 컴포넌트를 공용 UI에 넣거나 공용 UI에서 도메인을 import하지 않는다.
- 기존 UI 라이브러리가 `components/ui`를 소유하면 생성 코드는 그 관례를 유지할 수 있다. 앱의 모든 사용자 정의 코드까지 그곳에 추가하거나 라이브러리 컴포넌트를 무의미하게 재포장하지 않는다.
- 화면들이 공유하는 shell, navigation, content container, page header는 적절한 레이아웃으로 조합한다. 다른 화면의 필요를 수십 개 boolean prop으로 한 레이아웃에 밀어 넣지 않는다.
- 서버가 있으면 [구조와 경계](references/architecture.md)를 읽는다. 기존 아키텍처/ADR을 우선하고 요청 처리·업무 규칙·외부 접근의 책임을 최소한으로 분리한다. 서버가 필요 없는 범위에 서버를 만들지 않는다.

### 시각 규칙

- 의미별 색상, 간격, radius, elevation, content width와 반응형 규칙을 토큰으로 정하고 구현에서 실제로 참조한다. 반복되는 값을 화면마다 직접 쓰지 않는다. 일회성 예외는 공용 토큰으로 무조건 승격하지 않는다.
- 페이지 제목·섹션 제목·본문·보조 설명·라벨의 타이포그래피 위계를 정한다. 각 역할에 font family, size, weight, line-height를 지정하고 시맨틱 heading 구조와 함께 적용한다.
- 기준 문서와 실행 토큰의 원본/파생 관계를 정한다. 코드가 기존 원본이면 별도 문서를 경쟁 원본으로 만들지 않는다. DESIGN.md를 원본으로 채택했다면 구현 토큰과 일치하도록 유지한다.
- 제품 UI의 장식·상태·액션에 이모지를 사용하지 않는다. 기존 아이콘 세트 또는 Lucide 같은 일관된 라이브러리를 쓰고 크기·stroke 규칙을 맞춘다. 사용자 입력 콘텐츠는 이 규칙 때문에 변조하지 않는다.
- 아이콘 전용 액션에는 접근 가능한 이름을 제공하고 장식 아이콘은 보조 기술에서 숨긴다. 아이콘과 색상만으로 상태 의미를 전달하지 않는다.

### 동작과 데이터

- 각 데이터/상태의 소유자를 정한다. 공유해야 할 상태를 화면별로 복제하지 않고, 일회성 로컬 상태를 전역 저장소로 올리지 않는다. 계산 가능한 값은 원본과 별개 상태로 중복 저장하지 않는다.
- 경로·검색·필터의 URL 반영과 새로고침/뒤로가기 동작은 사용자 흐름에 맞춰 정한다. 저장의 의미와 유지 범위(세션/로컬/서버)를 명확히 한다.
- mock 데이터와 지연/실패 시뮬레이션은 교체 가능한 데이터 경계에 둔다. 화면마다 fixture와 fetch를 복제하지 않는다. mock 성공을 실제 서버 저장·인증·결제로 표현하지 않는다.
- 비동기 화면과 폼에 필요한 loading, empty, error, success, validation, disabled 상태를 정한다. 실제로 해당하지 않는 상태를 기계적으로 추가하지 않는다.

### 웹 프론트엔드의 Storybook

웹 프론트엔드 프로토타입에는 기본적으로 Storybook을 연동한다. 비웹 프로젝트에는 적용하지 않으며, 사용자가 제외했거나 프레임워크 지원 제약이 있으면 그 범위와 이유를 명시한다. 웹이라는 이유로 기존 설정을 재생성하거나 버전을 일괄 업그레이드하지 않는다.

[Storybook 구성과 상태 재현](references/storybook.md)을 읽고 프리미티브·공용 레이아웃/패턴·도메인 컴포넌트·도메인 화면을 구분한다. **자식 프래그먼트의 단독 스토리는 부모 화면 스토리를 대체하지 않는다.** 탭/단계별 프래그먼트와 그 상태를 실제 부모 레이아웃 안에서도 바로 재현할 수 있어야 한다. Storybook 작업은 마지막 부록이 아니라 해당 컴포넌트와 화면 구현에 함께 포함한다.

## 4. 흐름 단위로 구현하며 재사용 유지

1. 기반 토큰·레이아웃과 첫 핵심 흐름을 연결해 실행 가능한 단위를 만든다. 모든 화면의 정적 껍데기만 먼저 늘리지 않는다.
2. 컴포넌트·훅·유틸리티·서비스를 추가하기 **직전**, 기존 인벤토리와 코드를 이름뿐 아니라 책임·사용처로 검색한다. 기존 구현 재사용 → 조합/variant 확장 → 도메인 전용 구현 → 새로운 공용 추상화 순으로 적합성을 판단한다.
3. 같은 책임의 두 번째 구현이 생기면 그 시점에 통합한다. 기능이 다른 두 요소는 모양이 비슷하다는 이유로 합치지 않는다. 독립 구현이 필요하면 경계와 이유를 기준 기록에 간단히 남긴다.
4. 핵심 액션은 실제로 상태·데이터·경로를 바꾸도록 연결한다. 무반응 버튼, 링크 없는 내비게이션, 저장 없이 성공 toast만 표시하는 흐름으로 완료하지 않는다. 범위 밖 기능은 사용자가 오해하지 않게 명시한다.
5. 도메인 로직과 부수 효과를 렌더링 코드에서 분리하되, 한 번 쓰는 짧은 JSX까지 전부 별도 파일로 추출하지 않는다. 줄 수나 파일 수로 품질을 판정하지 않는다.
6. boolean 이름은 `is`, `has`, `can`, `should`, `needs` 접두사를 쓴다. 외부 API 계약의 이름은 경계에서 필요한 경우 변환하며 임의로 변경하지 않는다.

## 5. 검수 후 완료

[완료 검수](references/completion-review.md)를 읽고 이번 범위에 적용한다. 발견한 결함은 현재 요청 안에서 수정한 뒤 관련 검증을 다시 수행한다. 구현 직후 결과를 그대로 완료 보고하지 않는다.

최종 보고에는 구현한 흐름, 구조/재사용의 주요 결정, 실행 방법, 수행한 검증, mock과 미검증 범위를 간결히 남긴다. 사용자가 후속 요청으로 정리를 시켜야 하는 중복이나 고장 난 핵심 흐름을 선택적 개선으로 떠넘기지 않는다. 환경·권한·외부 서비스 때문에 막힌 항목은 완료한 부분과 구분한다.
