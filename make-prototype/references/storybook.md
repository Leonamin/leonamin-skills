# 웹 Storybook

**실제 컴포넌트와 부모 화면을 상태별로 직접 열어 검토할 수 있게 구성한다.**

## 연동과 분류

- 웹 프론트엔드에 기본 적용하고 기존 설정을 확장한다. 비웹·명시적 제외·지원 제약은 범위와 이유를 남긴다.
- 설치된 프레임워크·빌더·버전에 맞는 공식 연동을 확인한다. 앱의 토큰·폰트·스타일·provider를 공유하고 별도 화면 구현을 만들지 않는다.
- 탐색에서 프리미티브, 공용 레이아웃·패턴, 도메인 컴포넌트, 도메인 화면을 구분한다. 스토리는 코드 가까이에 두고 실제 variant·업무 상태를 다룬다. 모든 작은 JSX에 스토리를 만들지는 않는다.
- 개발·정적 build 명령을 제공하고 정적 산출물의 폰트·이미지·mock 리소스도 확인한다. 외부 호스팅은 요청받았을 때 수행한다.

## 부모·자식 계약

- 주요 프래그먼트는 단독 스토리와 실제 부모 화면 안의 재현을 함께 제공한다. 부모는 실제 header·탭·너비·여백·스크롤 영역을 유지한다.
- 각 탭·단계의 필요한 상태를 지정한 부모 스토리를 제공한다. 직접 URL이나 새로고침으로 수동 클릭 없이 해당 상태를 열 수 있어야 한다. 기본 탭만 있는 부모 스토리로 끝내지 않는다.
- 부모 안의 실제 탭·단계 전환도 동작해야 한다. 자식에 가짜 테두리를 두른 목업이나 숨긴 패널의 CSS 강제 노출로 대체하지 않는다.
- 부모와 자식은 같은 실제 컴포넌트·fixture·mock 계약을 사용한다. mock은 데이터·외부 서비스 경계에 두고 부모의 자식 UI를 mock으로 교체하지 않는다.
- decorator·공용 harness로 필요한 레이아웃과 provider를 제공하되 앱 shell을 중복 적용하지 않는다. 서버 경계 때문에 route를 가져올 수 없으면 앱·스토리가 같은 화면 조합을 사용하게 하고 미검증 서버 경계를 남긴다.

예: 결제 탭의 오류는 `OrderDetail/PaymentError`와 `PaymentPanel/Error`에서 같은 데이터를 사용해 재현한다.

## 상태 안정성

- route/query·args·초기 store/provider·데이터 adapter 등 앱의 실제 진입점으로 상태를 설정한다. Storybook 전용 boolean 렌더링 분기를 제품 코드에 넣지 않는다.
- 클릭으로만 생기는 상태는 해당 버전의 interaction/play 기능으로 재현하고 완료를 기다린다. 임의 sleep에 의존하지 않는다.
- 제품에 실제 발생하는 상태를 다루고 탭별 고유 상태·레이아웃 위험을 확인한다. 모든 상태와 viewport를 무조건 곱하지 않는다.
- 날짜·ID·데이터를 고정하고 router·store·cache를 스토리마다 초기화한다. 로딩은 유지 가능하게, 오류는 항상 재현 가능하게 만든다.
- mock 액션도 결과를 갱신한다. action 로그만 남기는 것은 동작 구현이 아니다. 실제 계정·운영 데이터·유료 요청에 의존하지 않는다.

## 검증과 인계

정적 build와 실제 렌더링을 각각 검증한다. 기본 탭 외의 부모 스토리를 직접 열고 새로고침하며, 탭 전환·좁은 화면·단독 자식의 같은 상태를 비교한다. 필요하면 기존 인벤토리에 `탭/단계 × 상태 → 부모·자식 스토리` 대응을 기록한다.

실행 명령·탐색 분류·주요 부모 상태 스토리·mock·미검증 범위를 전달한다. Storybook은 실제 앱 흐름 검증을 대체하지 않는다.
