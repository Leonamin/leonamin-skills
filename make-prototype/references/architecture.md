# 구조와 경계

**기존 아키텍처를 따르고, 변화 이유가 다른 책임만 분리한다.**

기존 ADR과 코드가 다르면 최신 근거를 확인한다. 임의로 대규모 이전을 시작하지 않는다. 새 프로젝트는 기능·도메인 중심으로 묶되 프레임워크의 라우팅·서버 관례를 우선한다.

## 책임과 의존성

| 책임 | 예시 |
| --- | --- |
| 앱 조립·라우팅·provider | `app/` |
| 도메인 독립 UI·스타일 | `shared/ui/`, `shared/styles/` |
| 화면·업무 UI·상태·데이터 접근 | `features/orders/` |
| 서버 요청·업무 규칙·외부 저장소 | `server/orders/` 또는 프레임워크의 서버 경계 |

경로는 예시다. 작은 기능은 소수의 응집된 파일로 시작하고 필요 없는 폴더·레이어·인터페이스를 미리 만들지 않는다.

- 앱·페이지가 도메인과 공용 코드를 조합하며 공용 UI는 도메인을 import하지 않는다.
- 도메인 간 협력은 소유자가 제공하는 경계를 사용하고 내부 파일의 무분별한 import·순환 참조를 피한다.
- 서버 업무 규칙을 request/response나 UI 상태에 묶지 않는다. 클라이언트에 서버 비밀값·DB 클라이언트를 넣지 않는다.
- 저장소 계층은 실제 외부 접근을 모을 때 둔다. 단순 호출마다 인터페이스·DI를 추가하거나 얇은 CRUD에 DDD·CQRS를 강제하지 않는다.

## 서버 계약

외부 입력은 경계에서 검증하고 업무 제약은 소유 위치에서 확인한다. 인증이 필요하면 서버에서 권한을 검증한다. UI 숨김만으로 제한하지 않는다. 비밀값은 서버 설정에서 읽고, 실패는 성공으로 바꾸지 않고 안정적인 오류로 전달한다. 다중 쓰기의 원자성 등 해당 흐름의 일관성을 보장한다.

프론트엔드 범위는 같은 계약의 mock adapter로 구현할 수 있다. 실제 권한 검증·서버 영속성을 구현했다고 주장하거나 교체를 위한 범용 백엔드를 만들지 않는다.

새 경계·의존성 등 유지보수에 영향을 주는 선택만 기존 문서에 남긴다. ADR이 필요하면 문맥·선택·대안·결과를 짧게 기록한다.
