# 구조와 경계

## 기존 프로젝트

기존 ADR과 코드가 정한 경계를 따른다. ADR(Architecture Decision Record)은 아키텍처 선택의 이유와 결과를 기록하는 문서이며 그 자체가 아키텍처 패턴은 아니다. 문서와 코드가 다르면 어느 쪽이 최신인지 근거를 확인하고 임의로 대규모 이전을 시작하지 않는다.

새 프로젝트는 기능/도메인 중심으로 묶고, 변화 이유가 다른 책임만 분리하는 것을 출발점으로 삼는다. 아래는 React/TypeScript의 예시이며 Next.js, Flutter 또는 다른 프레임워크의 라우팅·서버 관례를 대체하는 고정 템플릿이 아니다.

```text
src/
  app/                    # 앱 구성, 라우팅, provider
    layouts/              # AppShell 등 앱 공통 구조
  shared/
    ui/
      primitives/         # Button, TextField 등 도메인 독립 기본 요소
      layout/             # Stack, Container 등 실제 재사용되는 배치 도구
      patterns/           # EmptyState 등 도메인 독립 조합
    styles/               # 실행 토큰과 전역 스타일
  features/
    orders/
      pages/              # 화면 조립
      components/         # OrderSummary 등 주문 전용 UI
      model/              # 상태, 파생 값, 업무 규칙
      data/               # API adapter 또는 mock 구현
  server/                 # 서버가 필요한 경우만
    orders/
      handler.ts          # transport 입력 검증, 인증 컨텍스트, 응답 변환
      service.ts          # 업무 규칙과 작업 순서
      repository.ts       # 실제 DB/외부 저장소 접근이 있을 때
```

필요 없는 폴더·레이어·인터페이스를 미리 만들지 않는다. 작은 도메인은 여러 하위 폴더 대신 소수의 응집된 파일로 시작할 수 있다. 폴더 이름보다 다음 의존 규칙을 지키는지가 중요하다.

- 앱/페이지가 도메인과 공용 코드를 조합한다. 공용 UI는 특정 도메인에 의존하지 않는다.
- 도메인 사이에 협력이 필요하면 소유자가 제공하는 명시적인 경계를 사용한다. 다른 도메인 내부 파일을 무작위로 import하거나 순환 참조하지 않는다.
- 서버 업무 규칙은 request/response 객체나 UI 상태에 묶이지 않는다. 클라이언트 번들에서 서버 비밀값·DB 클라이언트를 import하지 않는다.
- 저장소 계층은 실제 외부 접근을 모으기 위해 둔다. 단순 함수 호출마다 추상 인터페이스/DI 컨테이너를 추가하지 않는다.
- 프레임워크의 server action/route handler도 동일한 책임 구분을 적용한다. 얇은 CRUD에 복잡한 DDD·CQRS를 강제하지 않는다.

## 서버가 실제로 수행할 일

입력 검증은 외부 경계에서 수행하고 업무 제약은 업무 규칙의 소유 위치에서 확인한다. 인증이 필요한 범위에서는 서버가 권한을 검증하며 UI 숨김만으로 제한하지 않는다. 비밀값은 서버 설정으로만 읽는다. 오류를 성공으로 바꾸지 말고 UI에 필요한 안정적인 오류 형태로 변환한다. 다중 쓰기의 원자성 등 실제 흐름에 필요한 데이터 일관성을 고려한다.

프론트엔드만 요청되면 같은 계약의 mock adapter로 동작을 만들 수 있다. 실제 권한 검증·서버 영속성이 구현되었다고 주장하지 않는다. mock 교체를 위해 모든 가능성에 대비한 범용 백엔드를 만들지 않는다.

## 결정 기록

새로운 경계나 의존성처럼 유지보수에 영향을 주는 선택만 기존 아키텍처 문서에 남긴다. ADR이 필요한 경우 문맥, 선택, 고려한 대안, 결과/제약을 짧게 적는다. 모든 컴포넌트에 ADR을 만들지 않는다.
