# UI Design Concept

**이미지로 디자인 방향과 상태별 화면을 제시하고, 구현에 필요한 의도와 조건을 전달한다.**

시안 요청으로 제품 소스·디자인 시스템·업무 정책을 바꾸지 않는다. HTML/CSS를 요청하면 그 형식을 따른다. 이미 구현까지 요청받았다면 시안을 이유로 승인을 반복 요구하지 않는다.

## 진행

1. 대상·사용자·주요 행동·화면 크기·언어를 파악하고 코드·문서·실제 화면·토큰을 확인한다. 시각 자료는 직접 본다. 확인 가능한 내용을 다시 묻지 말고 결과를 바꾸는 빈칸만 질문한다. 자료 접근이 막히면 한계와 진행 가능한 범위를 밝힌다.
2. 확인된 브랜드·탐색·데이터·가격·권한·행동을 보존하고, 탐색할 배치·강조·이미지 비중을 정한다. 새 기능은 제안으로 구분하며 새 화면의 미확정 내용은 가정으로 표시한다.
3. [상태 선택과 인계](references/states-and-handoff.md)로 정상·빈 데이터·로딩·오류·조건부 상태 중 필요한 범위를 정한다. 구조나 다음 행동이 달라지면 별도 화면, 작은 변화면 컴포넌트 비교로 보여준다. 사용자 지정 범위를 우선한다.
4. [생성 브리프](references/generation-brief.md)를 작성하고 실제 참고 이미지를 첨부해 생성한다. 제목을 반복하는 소개문은 [UI 문구 절제 기준](../design-product/references/ui-copy.md)으로 제거한다.
5. 선택한 대표 이미지를 참조해 상태를 확장한다. 방향 선택이 필요한 경우에는 후보를 먼저 보여주고 선택 후 확장한다. 확정된 방향과 공통 요소를 유지한다.
6. 결과 이미지를 직접 확인해 정보 누락·임의 기능·문구·날짜·금액 오류·잘림·상태 불일치를 수정한다. 수정할 수 없는 부분은 인계에 남긴다.

## 생성 기준

- 사용자 지정 도구를 우선하고 없으면 환경의 이미지 생성 기능을 사용한다. 실제 호출·참조·출력 규칙을 따르며 고정 모델·SDK를 요구하지 않는다.
- 일반 요청은 1안, 여러 방향 요청은 요청 수 또는 의미 있게 다른 2~3안으로 시작한다. 방향과 상태 화면의 수를 구분하고 비교할 화면 크기·언어·핵심 데이터를 맞춘다.
- 도구에 전달한 자료만 참조했다고 설명한다. 이미지 도구가 없으면 브리프·참고자료와 미생성 상태를 전달하고 다른 형식으로 임의 대체하지 않는다.

## 완료

이미지를 보여주고 방향·디자인 결정, 상태별 조건·행동, 제안 기능·미확정 정책과 구현 시 조정할 내용을 간결하게 전달한다. 이미지의 버튼·필터를 작동한다고 주장하지 않는다. 반응형·키보드·상태 전환은 구현 검증 대상으로 남긴다.

산출물은 플랫폼 디렉터리 또는 저장소 밖 작업 디렉터리에 둔다. 브리프·프롬프트·상태 정보·결과 경로나 식별자를 짧은 인계 문서에 묶는다. 로컬 저장이 불가능하면 응답으로 전달하고 저장했다고 주장하지 않는다. 구현으로 이어갈 때 선택 이미지와 인계를 사용하며 불필요한 중간 목업을 다시 만들지 않는다.
