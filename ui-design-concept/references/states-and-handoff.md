# 상태 선택과 구현 인계

## 상태 선택

다음은 조사 관점이다. 모든 화면에 일괄 적용하거나 모든 조합을 생성하지 않는다.

| 상태 | 확인할 차이 |
| --- | --- |
| 정상 | 핵심 정보의 우선순위와 주요 행동 |
| 전체 빈 데이터 | 처음 사용하는 상황의 설명과 다음 행동 |
| 검색·필터 결과 없음 | 조건 해제·검색 수정 등 전체 빈 상태와 다른 복구 행동 |
| 초기 로딩 | 아직 데이터가 없는 구조, 스켈레톤과 레이아웃 안정성 |
| 갱신·추가 로딩 | 기존 데이터를 유지할지, 어느 부분에 진행 상태를 표시할지 |
| 전체 조회 실패 | 오류 범위, 재시도와 대체 행동 |
| 일부 데이터·이미지 실패 | 정상 영역 유지와 부분 대체 표현 |
| 업무 상태 | 결제 대기·취소 등 실제 계약에 따른 정보와 가능한 행동 |
| 권한·접근 조건 | 해당 프로젝트에 존재하는 비로그인·권한 없음·접근 제한 |
| 콘텐츠 경계 | 긴 제목, 누락 이미지, 많은 항목 등 레이아웃이 달라지는 조건 |

상태별로 `노출 조건 / 보이는 정보 / 가능한 행동 / 근거 또는 가정 / 산출물`을 기록한다. 조건이 겹치면 실제 코드·정책에서 우선순위를 확인한다. 확인되지 않은 복구 방법이나 업무 정책을 디자인만으로 확정하지 않는다.

예를 들어 예약 화면에서는 다가오는 예약만 없음과 예약 전체 없음의 내용이 다르다. 취소 배지만 달라지면 컴포넌트 비교로 충분하지만, 결제 대기에 별도 행동이 있으면 그 영역 또는 화면을 보여준다. 정상 카드 구조가 정해진 후 같은 구조로 로딩·오류를 확장한다.

시안을 생략할 때는 기존 공용 상태 컴포넌트로 충분한지, 다른 시안과 구조가 같은지 등 이유를 적는다. 상태표만 작성하고 필요한 상태 이미지까지 생성했다고 주장하지 않는다.

## 인계 내용

짧은 Markdown 문서에 다음 정보를 묶는다. 새 프로젝트 문서 체계나 구현 전용 스킬은 필요하지 않다.

- 선택한 방향과 이미지 식별자; 선택 전이면 후보임을 표시
- 유지할 디자인 의도: 정보 위계, 주요 행동, 상태별 구조, 브랜드 표현
- 구현에서 조정할 세부사항: 정확한 간격·크기, 반응형, 공용 컴포넌트 매핑
- 상태표와 근거; 제안한 기능과 미확정 정책을 별도 표시
- 참고자료, 생성 프롬프트와 결과 경로 또는 식별자
- 구현 검증 항목: 실제 데이터·긴 콘텐츠·키보드·반응형·상태 전환

이미지와 확인된 정책이 충돌하면 정책을 보존하고 이미지의 수정 필요점을 밝힌다. 이미지에서 누락된 상태나 행동을 구현에서 삭제하지 않는다.
