# 제품 디자인

**사용자 목표와 주요 행동에 맞는 정체성·정보 구조·디자인 기준을 정하고, 기존 시스템에 필요한 변경만 적용한다.**

## 진행

1. 제품 브리프, 관련 화면, DESIGN.md·코드 토큰·Figma를 확인해 현재 기준을 찾는다.
2. 사용자 목표와 주요 행동을 바탕으로 정보 우선순위와 시각 방향을 정한다. 실제 트레이드오프가 있을 때 대안을 비교한다.
3. 기존 토큰·컴포넌트를 우선한다. 새 시스템이나 컴포넌트 범위가 불명확한 작업에는 `$component-inventory`로 필요한 범위를 정한다. Gallery 전체를 구현 목록으로 삼지 않는다.
4. 토큰·컴포넌트 계약의 기준을 하나로 유지한다. DESIGN.md가 기준이면 `$manage-design-md`를 사용하고, 코드·Figma가 기준이면 요청 없이 기준을 이전하거나 경쟁 JSON을 만들지 않는다.
5. 상담에는 제안을, 구현 요청에는 요청 범위의 변경을 제공한다. 문서는 기존 위치에 필요한 만큼 갱신하고, 제안·기억 기록은 요청받았을 때 남긴다.

확인하지 않은 브랜드 주장·수치·후기·기능을 만들지 않는다. 제목을 반복하는 소개문을 제거하고 [UI 문구 절제 기준](references/ui-copy.md)을 적용한다.

## 조건부 참고

기존 `design-product/` 디렉터리 체계를 운영할 때만 읽는다. 일반 작업에 별도 디렉터리나 manifest를 만들지 않는다.

- 기존 구조 변경: [design-system.md](references/design-system.md)
- 해당 체계의 초기화를 요청한 경우: [init.md](references/init.md)
- 디자인 기억 기록을 요청한 경우: [memory.md](references/memory.md)

결과에는 결정과 이유, 변경 파일, 검증과 남은 가정을 간결하게 남긴다.
