# 동작 다이어그램

요청에서 알고 싶은 동작을 중심으로 하나의 다이어그램을 만든다. 사용자가 형식을 지정하면 그 형식으로 그리고, 그 외에는 아래 기준을 사용한다. 선택한 형식의 참조만 읽는다.

| 질문의 초점 | 형식과 참조 |
| --- | --- |
| 누가 누구를 호출하고 무엇을 돌려주나? 한 시나리오에서 어떤 일이 어떤 순서로 일어나나? | 기본값인 [시퀀스](references/sequence.md) |
| 조건마다 다음 단계나 재시도 경로가 어떻게 갈라지나? | [흐름도](references/flowchart.md) |
| 한 대상이 어떤 사건과 조건에서 상태를 바꾸나? | [상태 전이](references/state.md) |
| 어떤 작업이 병렬로 실행되고 무엇을 기다린 뒤 다음 단계로 가나? | [UML 활동 다이어그램](references/activity.md) |
| 각 작업은 누가 맡고 어디서 책임이 넘어가나? | [스윔레인](references/swimlane.md) |

호출 흐름에 짧은 성공·실패 분기만 있으면 시퀀스 안에서 표현한다. 병렬 실행과 담당자 인계를 함께 읽어야 하면 활동 다이어그램에 스윔레인을 넣고 두 참조를 읽는다. 전체 분기와 특정 경로의 호출 상세처럼 한 그림에 섞으면 읽기 어려운 질문이 함께 있을 때만 보조 그림을 만든다.

## 설계 → 배치 → 렌더링 → 검증

1. **범위를 확정한다.** 시작 사건과 종료 결과, 설명할 시나리오를 먼저 정한다. 실제 동작을 그릴 때는 제공된 자료와 필요 범위의 코드·문서에서 참여자, 동작 순서, 분기 조건을 확인한다. 확인할 수 없는 내용이나 예시로 가정한 동작은 그림이나 설명에서 밝힌다.
2. **관계를 정한 뒤 배치한다.** 형식에 맞춰 참여자와 메시지, 단계와 조건, 상태와 사건, 병렬 작업이나 담당 역할을 정리한다. 읽는 방향을 유지하고 여러 화살표가 같은 구간을 지나면 간격을 넓히거나 연결 위치를 옮긴다. 연결선을 배치할 때 도형과 라벨이 차지하는 영역을 함께 고려한다.
3. **한 원본에서 렌더링한다.** 결과를 볼 환경에 맞춰 Mermaid, PlantUML 등 표기법을 지원하는 렌더러를 고른다. 간단한 설명은 대화에서 바로 볼 수 있는 다이어그램을 우선한다. 파일이 필요하면 편집 가능한 다이어그램 원본에서 SVG를 렌더링하고, HTML이 필요하면 SVG를 포함한 단일 파일을 만든다. PNG도 필요하면 같은 SVG나 HTML을 캡처한다. 프로젝트 도구나 요청 형식에 맞는 기존 경로가 있으면 그 경로를 쓴다.
4. **의미와 화면을 검증한다.** 시작부터 각 종료 지점까지 읽으면서 참조의 형식별 검증 항목을 확인한다. 사용 가능한 렌더러로 결과를 열고 실제 열람 크기에서 글자와 화살표 겹침, 라벨의 연결 대상, 잘림을 확인한다. 문제가 있으면 원본을 수정하고 다시 렌더링한다. 렌더링할 수 없는 환경에서는 편집 가능한 원본을 제공하고 렌더링 확인 범위를 밝힌다.
